1. Product Vision
The platform is a modern Web-GIS decision-support system for understanding urban ecological conditions, land-use change, accessibility, and facility connectivity.
The interface combines the interaction model of Google Maps with a more restrained, editorial and premium visual language inspired by Zara.
Design principle
“The map is the product. The interface should disappear when the user is exploring it.”
2. Source-Aligned Product Scope
The supplied database design adds Module G (Connectivity Reporting), including a ROAD_NETWORK table for OSM/pgRouting topology and a FACILITY_CONNECTIVITY table for cached nearest-facility results.
Road-network topology supports shortest-path and isochrone queries.
Connectivity results cover hospitals, schools and major roads/highways.
Results include network distance, travel time and route geometry.
Connectivity supports driving and walking modes.
Public, view-only sharing is supported through a shareable token.
Existing analyst modules A–F remain centered on LULC, NDVI, UHI and AHP/TOPSIS.

33. Map Data Strategy
Import the district-level OSM road network once.
Build pgRouting topology once during initialization.
Query the pre-built network for shortest paths and isochrones.
Pre-generate static map tiles where appropriate.
Use PMTiles / MBTiles for static tile delivery when suitable.
Avoid running OSMnx on every user request.
34. Performance Principles
Use vector tiles wherever possible.
Use optimized raster overviews.
Use the pre-built pgRouting graph.
Cache connectivity results.
Lazy-load analytical modules.
Do not load every GIS layer simultaneously.
Split study areas into zones if free-tier storage limits are reached.

38. Design North Star
Can I understand the map immediately?
Can I find a location in under 5 seconds?
Can I access analysis without opening a complicated dashboard?
Can a non-GIS citizen understand the connectivity result?
Does the interface look premium without becoming decorative?
